## B-001 舌象拍照要能拉近（可调焦）★ 下一版做

**来源**：2026-10-08 医师反馈（用户在真机验收摄像头修复后提出）
**状态**：**已确认、明确推迟** —— 用户原话："这一点先记住，不开刀，等下个版本再完善"
**前置**：摄像头已能在 Windows 11 与 macOS 正常调用并拍照（v0.1.23 的 `device.camera` entitlement 修复生效）

### 问题

现在拍出来的是**整张头像**，舌象在画面里太小、看不清 ✗ —— 这直接削弱了"拍舌象"的意义：
舌质、舌苔、润燥这些**恰恰要靠细节判断**，看不清等于没拍。

### 要做到什么（验收标准）

1. 取景时能把画面**拉近到以舌部为主体**（舌体占据画面主要区域），并**所见即所拍**；
2. 拉近后**细节仍可用**：舌体区域的实际像素不低于约 600×600（低于这个数放大只是糊）；
3. 放大倍数可调（不是只有"1× / 最大"两档），且操作在取景框内完成、不需要命令行；
4. 不支持硬件变焦的设备上**也必须能拉近**（见下：数字裁切兜底）；
5. 不破坏现有链路：拍到的照片仍然走同一条附件链路交给 Dify（内核只看 dataUrl）。

### 技术路线（两条都要，硬件优先、数字兜底）

**① 硬件变焦（能用就用）**
```js
const caps = track.getCapabilities?.();          // 可能没有 zoom 字段
if (caps?.zoom) {
  await track.applyConstraints({ advanced: [{ zoom: 值 }] });   // 值须在 [min,max] 内、按 step 取整
}
```
- 注意：`getCapabilities()` 在部分平台**不存在**，`caps.zoom` 也常常没有 → 必须判存在，不能假定。
- Windows 下 UVC 摄像头较常见支持；**macOS 上多数内置/外接摄像头不暴露 zoom** ✗ → 所以必须有 ②。

**② 数字裁切（兜底，永远可用）**
在现有的画布泵帧管线里裁中心区域再放大（预览与拍摄用同一块画布，天然"所见即所拍"）：
```js
// sx, sy, sw, sh = 以画面中心为基准的裁切框（由缩放倍数决定）
ctx.drawImage(video, sx, sy, sw, sh, 0, 0, canvas.width, canvas.height);
```
- 同时把采集分辨率提到 `width: { ideal: 1920 }`：裁切后仍要有足够像素，否则只是把糊的放大。
- 建议再加一个"对准框"引导医师把舌部放进框内。

**③ 可选提升**：`ImageCapture.takePhoto()` 能拿**全分辨率**静帧，比画布抓帧更清晰；
但它并非所有平台都可用，必须 try/catch + 回落到画布。

### 不要做的事

- 不要为了拉近就去掉上下文：舌诊需要看到舌体整体，过窄的裁切同样无法判断。
- 不要把"放大"做成仅视觉放大（预览放大了、存下来的还是原图）—— 必须以**存下来的那张**为准。

### 怎么验

- 假设备路径（本机可跑）：`gui-verify/camera-e2e.js` 已能驱动真实页面点按钮、读画布像素，
  可扩展成"设 2× 后画布中心区域像素确有变化"。
- **真机必须人工看一眼**：拍一张自己的舌头，确认舌体在照片里占比足够、细节可辨。
  这一条我这边测不了（本机无 `/dev/video*`），只能由医师验收。

## B-002 拍完不满意要能取消重拍 ★ 下一版做（与 B-001 一起）

**来源**：2026-10-08 医师反馈
**状态**：**已确认、明确推迟** —— 用户原话："也是不动刀，先记着，下个版本一起完善"
**配套**：与 B-001（可调焦拉近）同属"拍照体验"，建议同一版一起做

### 问题（已核实现状，不是推测）

界面上与舌象照片有关的只有两个按钮：`📷 摄像头拍照`、`📁 选择图片`（`index.html:71-72`），
拍完只显示一张小缩略图（`#thumb`，`index.html:87`）。而 `pendingAttachments` 只在**两处**被清空
（`consult.js:358` 文件对话框取消、`consult.js:510` 消息已发送之后）—— 也就是说：

- **拍完想撤掉这张照片，界面上没有入口** ✗（只能去点"选择图片"再点取消，属于没人能发现的路径）
- **没有"重拍"这个动作** ✗（虽然再点一次"摄像头拍照"确实会重开，但界面上没有任何提示）
- 缩略图很小 ✗，**看不清拍糊了没有** —— 而"要不要重拍"恰恰取决于看得清

### 要做到什么（验收标准）

1. 拍完之后有明确的 **「重拍」** 与 **「移除」** 两个动作，一眼可见，不需要"知道"；
2. 拍完能**看清**结果（可放大预览/点开看大图），据此判断是否需要重拍；
3. 「重拍」= 重新打开取景框并**丢弃**上一张（不能两张都留着）；「移除」= 回到"未附照片"状态；
4. 未附照片时**不显示**这两个按钮（避免常驻噪音）；
5. 拍照取景框内的「取消」语义要一致：取消 = 不改变当前的已附状态（而不是悄悄清空）。

### 技术要点

- 现有附件链路是单一对象：`pendingAttachments = [{ type:'image', name, dataUrl }]`
  （`consult.js:349`）—— 重拍与移除都只是"替换/清空它 + 同步缩略图与提示文案"，
  改动面很小；关键是**入口要显眼、状态要一致**。
- 缩略图放大预览可复用现有大图查看能力（若问诊正文里的图片已有点开看大图，直接复用同一套）。
- 三处状态必须同步：`pendingAttachments`、`#thumb`、`#tongueTip` ——
  任何一处漏改都会出现"提示说已附上、实际没附"这类最难查的错位。

### 怎么验

- 假设备路径：扩展 `gui-verify/camera-e2e.js` —— 拍一张 → 断言缩略图显示 →
  点「移除」→ 断言 `pendingAttachments` 为空且缩略图隐藏 → 再拍 → 点「重拍」→ 断言只有一张。
- 真机人工：拍一张糊的，确认能一眼看到"重拍/移除"，且移除后发送的消息**不带附件**。

## B-003 Electron 31 已 EOL（锁定但未升级）★ 待你决定

**来源**：2026-10-09 接手后第一期整改时发现（依赖锁工作做的副产品）
**状态**：**已锁定版本，未升级** —— 升级属于行为变更，不在"不改功能行为"的第一期范围内

### 现状

`tools/tcm-ui/desktop/package.json` 声明 `electron: "^31.0.0"`，实际装的是 **31.7.7**。
Electron 31 已过官方支持期（官方只维护最近三个大版本，每个约半年），
也就是说：**已知的安全问题不会再有补丁**，而这是拿去装在医师电脑上的桌面应用。

一期做的是**锁定**（新增 `package-lock.json`，并把打包工作流的 `npm install` 改成 `npm ci`），
这让"装出来的到底是哪一版"变成确定的事 —— 但不解决"这一版已经不再被维护"。

### 为什么没顺手升上去

Electron 跨大版本升级会牵动：打包配置（electron-builder）、mac 的 entitlements/notarize、
以及摄像头那条链路（v0.1.23 刚修好的 `device.camera` 授权就是在**当前这个版本**下验过的）。
摄像头是**真机才能验**的，我这边没有图形环境 —— 在这里顺手升，等于把一个"验不了"的改动
塞进一次以"防复发"为目标的迭代里。所以：先锁住，升级单独排期，升级后**必须真机复验摄像头**。

### 怎么验

- 升级后跑 `npm test`（含 `desktop-orchestrator` 档）+ `node tools/preflight.mjs`；
- **真机**：三平台各装一次，确认能起、能问诊、**摄像头能出图**（B-001 的验收也要重跑一遍）。

## B-004 preflight [2]「打包布局」档间歇性失败 ★ 待观察

**来源**：2026-10-09 跑 `node tools/preflight.mjs --quick` 时遇到一次

### 现象

`[1] 门禁` 11 档全绿（其中 `desktop-orchestrator` 25 项通过），紧接着 `[2] 打包布局`
**再跑一次同一个测试**时失败在「问诊台自带端点可用：/api/tcm/patients + /api/tcm/reminders」。

### 已排除 / 未定位

- 单独跑该测试 **5/5 通过**；按"先跑全量 11 档再造 dist 再跑"复现一次，**也通过**。
  所以没能稳定复现，根因**未定位**。
- 端口不是固定端口（随机端口 + 6 次重试），所以不是简单的端口占用。
- 怀疑方向：`startApp()` 返回后没有任何"就绪等待"，紧接着的第一个请求在系统繁忙时可能落空。

### 不做的事

**不给测试加重试来"修好"它。** 重试只会把间歇失败藏起来 —— 而 preflight 是"能不能打 tag"
的判据，一条会随机变红的判据和一条永远绿的判据一样不可用。要么找到根因，要么就这样记着。

### 怎么验

- 记录每次 preflight 的 [2] 结果；若再出现，抓当时的完整输出（特别是端点返回的状态码/错误体）。
- 若确认是缺就绪等待，修法是在 `startApp()` 里等内核与问诊台各自**真的能应答**再返回
  （不是等固定毫秒数 —— 那只是把概率变小，不是修）。

## B-005 Dify `conversationId` 是单例（并发会串病历）★ 已知风险，未动

**来源**：代码阅读（`layer/providers/dify.mjs`：`let conversationId = ''`，文件级单例变量）
**关联**：`layer/packs/tcm/README.md` §四 4.1 路线 B 里已经点名过这一条

Provider 实例内的 `conversationId` 只有一个，不按患者隔离。当前"一问诊一实例"的用法下不会出问题，
但一旦同一进程内并发服务两个患者，两人的 Dify 会话会串 —— 而串会话在病历上的表现就是串病历。
**未动**：修它要改会话隔离方式，属于行为变更，且需要真实 Dify 环境才能验（现有测试全是桩）。
